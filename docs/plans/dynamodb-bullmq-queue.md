# Add DynamoDB + BullMQ Queue to chat-example

## Context

Goal is educational: learn how a message queue moves data end-to-end. Today `backend/src/services.ts` fakes this with `setTimeout` calls straight into an in-memory `Map` (`store.ts`) — there's no real DB and no real queue anywhere in the repo. This plan replaces that simulation with a real pipeline:

**frontend → `sendMessage` mutation → BullMQ job enqueued → worker processes job → DynamoDB write → status-progression delayed jobs → pubsub publish → existing SSE subscription (`onMessageUpdate`) delivers to clients.**

The existing frontend optimistic-UI + subscription flow (`useChat.ts`) is already correct and needs no rework for single sends. Batch sending (user's "one or several messages at once" requirement) is handled by calling the existing `sendMessage` mutation N times in parallel — no new bulk mutation.

Decisions locked with the user:
- **DB**: DynamoDB Local via Docker, real AWS SDK v3.
- **Queue**: BullMQ + Redis via Docker.
- **Batch send**: N parallel calls to existing `sendMessage` mutation.
- **Status-progression delay**: separate BullMQ delayed jobs (`message-status` queue), not in-worker `setTimeout`/sleep — teaches the delayed-job pattern.
- **Worker**: separate process (`backend/src/worker.ts`, own `dev:worker` script) — real producer/consumer split.
- **Batch UI**: not built now. `useChat.ts` exposes `sendMessages(texts: string[])`; `MessageInput.tsx` stays untouched.
- **Test strategy**: two tiers — default `pnpm test` stays fast/mocked (no Docker), new opt-in `pnpm test:integration` hits real Docker services.
- **Conversation existence**: real DynamoDB item (`PK=CONVERSATION#id, SK=METADATA`), seeded on bootstrap — no in-memory Set.

## Phase 0 — Docker infrastructure

`/docker-compose.yml` (repo root):
```yaml
services:
  dynamodb-local:
    image: amazon/dynamodb-local
    ports: ["8000:8000"]
    command: ["-jar", "DynamoDBLocal.jar", "-sharedDb", "-dbPath", "./data"]
    volumes: ["dynamodb-data:/home/dynamodblocal/data"]
  redis:
    image: redis:7
    ports: ["6379:6379"]
    volumes: ["redis-data:/data"]
volumes:
  dynamodb-data:
  redis-data:
```
`-sharedDb` matters — without it DynamoDB Local partitions data per access-key/region.

Root `package.json` scripts: `"docker:up": "docker compose up -d"`, `"docker:down": "docker compose down"`.

## Phase 1 — DynamoDB table design

Single table `chat-messages` (name from env `DYNAMODB_TABLE_NAME`):
- **PK**: `CONVERSATION#<conversationId>`
- **SK**: for messages, `MESSAGE#<createdAtISO>#<messageId>` (ISO timestamps sort lexicographically → `Query` with `begins_with("MESSAGE#")` returns chronological order, no GSI needed). For conversation metadata: `SK = METADATA`.
- Message attributes: `id`, `body`, `senderId`, `senderName`, `status`, `createdAt`, `deliveredAt?`, `error?`.
- Conversation metadata item: `id`, `createdAt`.

Message `id` and `createdAt` are generated by the **producer** (`services.ts`), not the worker — this makes the SK deterministic everywhere downstream (worker knows the exact key to `UpdateItem` without a lookup GSI).

Bootstrap seeds `conversation-1` as a real `CONVERSATION#conversation-1 / METADATA` item (replaces the old in-memory Map seed).

## Phase 2 — DB client module (`backend/src/db/`)

- **`client.ts`** — `DynamoDBClient` from `@aws-sdk/client-dynamodb`, endpoint from `DYNAMODB_ENDPOINT` (default `http://localhost:8000`), wrapped in `DynamoDBDocumentClient.from(client, { marshallOptions: { removeUndefinedValues: true } })`. Local dev needs dummy `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` (SDK requires *something* present even though DynamoDB Local ignores them).
- **`bootstrap.ts`** — `ensureTableExists()`: `DescribeTable` → catch `ResourceNotFoundException` → `CreateTable` (PK/SK schema above, `BillingMode: PAY_PER_REQUEST`), then `ensureConversationSeeded('conversation-1')` (conditional `PutCommand`, idempotent). Gated by `DYNAMODB_AUTO_CREATE_TABLE=true` so it's a no-op against real AWS.
- **`messagesRepo.ts`** — replaces `store.ts`'s persistence half, same function shapes so `schema.ts` changes minimally:
  - `conversationExists(conversationId): Promise<boolean>` — `GetCommand` on `METADATA` SK.
  - `putMessage(conversationId, message: Message): Promise<void>` — `PutCommand`.
  - `updateMessageStatus(conversationId, createdAt, messageId, patch: StatusPatch): Promise<Message>` — `UpdateCommand` keyed by the deterministic SK.
  - `getConversationMessages(conversationId): Promise<Message[]>` — `QueryCommand`, `begins_with(SK, "MESSAGE#")`, `ScanIndexForward: true`.

`store.ts` keeps only `pubsub` (orthogonal to persistence, must stay for `onMessageUpdate`). The `conversations` Map and `addMessage`/`updateStatus` persistence logic move to `db/messagesRepo.ts`.

## Phase 3 — Queue module (`backend/src/queue/`)

- **`connection.ts`** — shared `ioredis` instance from `REDIS_URL` (default `redis://localhost:6379`), `maxRetriesPerRequest: null` (BullMQ requirement).
- **`messageQueue.ts`** — `export const messageQueue = new Queue('send-message', { connection })`. Job payload: `{ conversationId, messageId, body, senderId, senderName, createdAt }` (id/createdAt generated by producer).
- **`statusQueue.ts`** — `export const statusQueue = new Queue('message-status', { connection })`.
- **`messageWorker.ts`** — `Worker('send-message', processor, { connection })`. Processor:
  1. `messagesRepo.putMessage(...)` with `status: 'queued'` (no pubsub publish — preserves "queued invisible to peers" invariant).
  2. Enqueue two jobs on `statusQueue`: `delay: SENT_DELAY_MS` (patch `{status:'sent'}`), `delay: DELIVERED_DELAY_MS` (patch `{status:'delivered', deliveredAt}`).
- **`statusWorker.ts`** — `Worker('message-status', processor, { connection })`. Processor: `messagesRepo.updateMessageStatus(...)` then `pubsub.publish(...)` — this is where `onMessageUpdate` keeps firing exactly as today.
- **`index.ts`** — barrel exporting `startWorkers()` (constructs both `Worker` instances).

## Phase 4 — Wiring

- **`services.ts`**: `sendMessage(...)` generates `id`/`createdAt`, calls `messageQueue.add('send-message', payload)`, returns a `Message` object with `status: 'queued'` immediately (mutation stays synchronous-feeling — do not await the worker). `schema.ts`'s mutation resolver is untouched except swapping the conversation-existence check to `messagesRepo.conversationExists(...)`.
- **`server.ts`**: add `await ensureTableExists()` before `server.listen(...)`. No worker startup here (separate process).
- **New `backend/src/worker.ts`**: `await ensureTableExists()` then `startWorkers()`. New script `"dev:worker": "tsx watch src/worker.ts"` in `backend/package.json`. Dev now requires two terminals: `pnpm dev:backend` + `pnpm dev:worker` (document in README).

## Phase 6 — Test strategy

**Tier 1 (default `pnpm test`, no Docker)** — mock `@aws-sdk/lib-dynamodb` client `.send` and BullMQ `Queue`/`Worker` at the module boundary (`vi.mock`):
- `store.test.ts` → rewritten as `db/messagesRepo.test.ts`: asserts repo functions call `send()` with correctly-shaped `PutCommand`/`QueryCommand`/`UpdateCommand` inputs.
- `services.test.ts`: asserts `messageQueue.add` called with correct job name/payload (mock the queue module) — decoupled from real Redis and from `vi.useFakeTimers()` timer progression.
- New `queue/messageWorker.test.ts`: invokes the worker's processor function directly (BullMQ exposes it as a plain async function, testable without a live connection) with mocked `statusQueue.add` calls — this is where the old fake-timer status-progression test logic moves.
- `app.test.ts`: keep the immediate `queued` mutation-response assertion and the hidden-until-sent query assertion, but seed a DynamoDB-mocked item directly at `sent` status rather than waiting on real timer progression (drop the `vi.advanceTimersByTimeAsync(3000)` pattern — BullMQ's delayed-job scheduler isn't intercepted by fake timers).

**Tier 2 (opt-in, `pnpm test:integration`)** — new `backend/test/integration/` directory, requires `pnpm docker:up` first, not wired into default `pnpm test` or CI-blocking path. At least one test: send a message via `yoga.fetch()`, poll DynamoDB (or subscribe to pubsub) until status reaches `delivered`, assert final DB state. This is the layer that actually proves the real end-to-end pipeline.

## Phase 7 — Frontend change (batch send plumbing only)

`frontend/src/hooks/useChat.ts` — add alongside existing `sendMessage` (don't change its signature):
```ts
const sendMessages = useCallback(
  async (texts: string[]): Promise<void> => {
    await Promise.all(texts.map((text) => sendMessage(text)))
  },
  [sendMessage],
)
```
Return `sendMessages` from the hook's result object (extend `UseChatResult` interface). Each parallel `sendMessage(text)` call independently creates its own `optimistic-${uuid}` and calls `submitOutbound` — N parallel calls naturally produce N optimistic rows and N independent mutation round-trips. No changes to `chatService.ts`, `schema.ts`, or `MessageInput.tsx`/`ChatPage.tsx` — UI wiring is a follow-up, not part of this change.
